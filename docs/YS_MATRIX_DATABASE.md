## 4. Relationships (tenant/ownership core)

```
Showroom 1──* User
Showroom 1──* Inventory, Supplier, Customer, Sale, Expense, AuditLog, Notification, Subscription
User    1──* RefreshToken, PasswordResetToken, Sale (as seller)
Supplier 1──* SupplierPayment, Inventory (nullable)
Sale    1──* SaleItem (snapshot) 1──* Installment
Sale   *──1 Customer (nullable, SET NULL)
```

- All tenant tables cascade from `showrooms` (tenant deletion wipes tenant data — no recycle/archive; RISK note in Discovery Report).
- `SaleItem.inventory` = RESTRICT — sold items cannot be hard-deleted; soft-delete (is_active) is the only archive path (implemented 2026-07-04).
- `Sale.user` = RESTRICT — a user with sales can never be deleted, only deactivated (consistent with soft-delete policy).

## 5. Indexes & Constraints (FACT)

- Unique: `showrooms.slug`, `users.email`, `refresh_tokens.token`, `password_reset_tokens.token_hash`, `sales(showroom_id, invoice_number)`, `scheduled_job_runs(job_name, run_key)`
- Notable composites: `inventory(showroom_id, vehicle_type)`, `inventory(showroom_id, status)`, `inventory(showroom_id, is_active)` + partial `idx_inventory_active`, `sales(showroom_id, sold_at)`, `sales(showroom_id, status)`, `installments(due_date, is_paid)`, `expenses(showroom_id, expense_date)`, `audit_logs(showroom_id, entity)`, `audit_logs(showroom_id, created_at)`, `customers/suppliers(showroom_id, is_active)`, `notifications(showroom_id, is_read)`
- Missing index opportunity (not a bug at current scale): `inventory(showroom_id, is_active, status)` for low-stock+active queries; search columns rely on `LIKE '%…%'` without trigram GIN indexes (see Performance Audit).

## 6. Soft-Delete & Snapshot Policy (FACT)

- Customers (v1.1), Suppliers (v1.1), Inventory (2026-07-04): `is_active` flip; no DELETE SQL in application paths (verified: `deleteItem` and customer/supplier deletes are archive ops).
- Sale items carry immutable invoice snapshots since v1.1 — items sold later don't reflect inventory edits.
- Consequences: nothing is ever truly deleted — audit-friendly, but data can accumulate (e.g., archived inventory, disabled users, notification rows; `deleteOldNotifications` cleans read notifications >30 days).

## 9. Observations for the Lead Architect

1. **Denormalized supplier balances** (`total_due/total_paid`) — updated in-transaction; consistent today, but no ledger/reconciliation mechanism if a payment ever fails mid-flight (edge handled via transaction rollback — FACT).
2. **Refresh tokens stored raw** (JWT string, unique column) — a DB leak exposes live session tokens; rotation + short TTL mitigate, but hashing would be stronger (RECOMMENDATION, MEDIUM).
3. **Tenant-wide cascade delete** on showrooms — total data loss path if a showroom_id FK ever fired unexpectedly; SuperAdmin has no showroom-delete endpoint, so no active path exists today (INFORMATIONAL).
4. **Money types**: DECIMAL(12,2)/(10,2) — appropriate; no float money observed (FACT).
5. **No soft-delete for sales/licenses/subscriptions** — sales are cancelled (status), not deleted; subscription/license records are historical by design.
6. Schema comments document the *reasoning* of key audit fixes — unusually good forensic documentation; treat schema.prisma as the authoritative model doc until contradicted.
